## DETALHAMENTO POR ÁREA (ATUALIZADO)

### 1. BANCO DE DADOS SQLITE ✅ PASS
- 19 tabelas conforme schema `0001_initial_schema.sql`
- Constraints UNIQUE e FKs implementadas
- Pragma `journal_mode = WAL` para performance e concorrência
- Parser nativo `.env`; backup automático evitado (single file)

### 2. AUTENTICAÇÃO JWT ✅ PASS
- Middleware `authenticateToken` valida `Authorization: Bearer <token>`
- `JWT_SECRET` configurável via `.env` (fallback seguro de desenvolvimento)
- `JWT_EXPIRES = 8h` padrão
- Rotas:
  - `POST /api/auth/register` — cria usuário STUDENT (ADMIN só por promoção)
  - `POST /api/auth/login` — bcrypt compare + retorno JWT sem hash
  - `POST /api/auth/logout` — apenas auditoria (JWT é stateless)
  - `GET /api/auth/me` — retorna `req.user` sem hash de senha
- **Segurança**: senha de admin nunca é logada; origem é logada apenas se conhecido.

### 3. RBAC (STUDENT / ADMIN) ✅ PASS
- `requireRole(...roles)` — exige papel ou 403
- `requireSelfOrAdmin(getIdFn)` — protege recursos contra IDOR/BOLA (próprio usuário ou ADMIN)
- Rotas `/api/admin/*` aplicam middleware global `router.use(authenticateToken, requireRole('ADMIN'))`
- Testes validam: STUDENT 403 em /admin; ADMIN 200 em /admin; cross-access negado.

### 4. SIMULADO FINAL ✅ PASS
- **PASS_SCORE = 23/30** (76,67%)
- 30 questões ativas (`is_active=1`); ordem determinística
- Cálculo **100% server-side**: score enviado pelo cliente é TOTALMENTE ignorado
- Resposta para STUDENT: **`{attempt_id, result: "APROVADO" | "NÃO APROVADO"}`** (sem score, sem acertos, sem gabarito)
- Resposta para ADMIN em `/api/admin/attempt/:id`: score, correct, wrong, pergunta, dada, correta, categoria
- Testes passam: 22/30 → NÃO APROVADO; 23/30 → APROVADO; 30/30 → APROVADO; spoof de score 30 → NÃO APROVADO (0 acertos calculados)

### 5. SEGURANÇA (IDOR / BOLA) ✅ PASS
- Testes na suíte validam 4 cenários de cross-access: A cria progresso próprio; B tenta ler progresso de A → 403; B tenta escrever progresso de A → 403; A tenta ler progresso de B → 403; ADMIN lê progresso de A → 200.

## 24. INTEGRAÇÃO FIREBASE ADMIN SDK + CLOUD FIRESTORE (NOVA — ETAPA CRÍTICA) ✅ PASS

### 24.1 Arquitetura Escolhida: Dual-Write Assíncrono (Source-of-Truth = SQLite)
O SQLite continua como fonte absoluta da verdade (sem latência, sem dependência de rede, sem lock-in). O Firestore é a réplica em nuvem, **consistência eventual unidirecional**.

| Camada | Arquivo | Responsabilidade |
|---|---|---|
| Inicialização Admin SDK | `server/services/firebase.cjs` | initFirebase(), getFirestore(), getAuth(), graceful fallback |
| Sync Orquestrador | `server/services/firestoreSync.cjs` | Fila assíncrona, bulk-sync, sync por entidade, merge-safe |
| Integração Rotas Auth | `server/routes/auth.cjs` | syncUserUpsert + syncAuditLog em register/login/logout |
| Integração Progresso | `server/routes/progress.cjs` | syncLessonProgressUpsert + syncAuditLog em POST/PATCH |
| Integração Simulado | `server/routes/quiz.cjs` | syncQuizAttemptUpsert (batch 30 answers) + syncAuditLog |
| Integração Checkpoints | `server/routes/checkpoints.cjs` | syncCheckpointAnswerUpsert + syncAuditLog |
| Bootstrap + Endpoints ADM | `server/index.cjs` | Inicialização não-bloqueante, Graceful Shutdown, /health com status, GET /api/firebase/status, POST /api/firebase/bulk-sync |

### 24.2 Coleções Sincronizadas no Firestore (8 coleções raiz + 1 subcoleção)
1. **`users/{userId}`** — id, email, name, identifier, role, role_id, is_active, created_at, updated_at, synced_at.
2. **`training_modules/{modId}`** — catálogo (acessível a todos autenticados via regras).
3. **`training_lessons/{lessonId}`** — conteúdo completo; campos JSON (images/documents/references) parseados com segurança.
4. **`lesson_progress/{progressId}`** — progresso por lição/usuário; UNIQUE garantido pelo SQLite.
5. **`quiz_attempts/{attemptId}`** — tentativa do simulado + **subcoleção** `answers/{answerId}` com batch write.
6. **`checkpoint_answers/{answerId}`** — respostas dos checkpoints de lição.
7. **`audit_logs/{logId}`** — auditoria completa; old_value/new_value parseados de JSON string se possível.
8. **Regras de segurança publicadas**: arquivo `firebase/firestore.rules` — **ZERO writes client-side; reads only-own-data para STUDENT; reads completos apenas ADMIN; default deny.**
9. **Índices compostos publicados**: arquivo `firebase/firestore.indexes.json` — 7 índices compostos + 1 field override para busca por email.

### 24.4 Graceful Degradation (Degradação Graciosa)
- Se credenciais não configuradas OU `FIREBASE_SYNC_ENABLED=false`:
  - Servidor **inicia normalmente** sem nenhum traceback sujo.
  - `/health` retorna `{firebase: {sync_enabled: true/false, initialized: true/false, init_error: "..."}}`
  - Chamadas a `sync*()` tornam-se **não-operações seguras** (if !canSync() return).
  - Toda a aplicação continua 100% funcional só com SQLite.
- **Graceful Shutdown**: sinais SIGINT/SIGTERM disparam `flushQueue()` com timeout 5s para entregar writes pendentes do Firestore antes de `process.exit(0)`.

### 24.5 Endpoints Administrativos do Firebase (AMBOS exigem token JWT de ADMIN)
1. **`GET /api/firebase/status`**
   - Retorna status do SDK, project_id, init_error, tamanho da fila.
   - **`queue_size`** é o campo canônico (esperado no roteiro do usuário). **`queue_pending`** é mantido como **alias retrocompatível** (`@deprecated` — ambos retornam o mesmo valor dinâmico `SYNC_QUEUE.length`). A remoção do alias está prevista para v3.0.
2. **`POST /api/firebase/bulk-sync`**
   - Executa `runFullBulkSync()` em todo o SQLite. Lê todas as tabelas, enfileira writes para o Firestore e aguarda flush completo. Ideal para **popular o Firestore VÁZIO (sua Figura 1)** com os dados históricos existentes antes da integração.
   - Retorno: `{ok:true, counts:{users, modules, lessons, lesson_progress, quiz_attempts, checkpoint_answers, audit_logs}}`.
3. **Evidência do dual-write em tempo real (logs `[FIRESTORE_SYNC]`)**
   - Além do bulk-sync (que migra o histórico), a escrita **dual-write em tempo real** é comprovada pelos logs do servidor a cada operação:
     `[FIRESTORE_SYNC] users/4 atualizado (email=adm@teste.com)`
     `[FIRESTORE_SYNC] lesson_progress/7 (user=5 lesson=2 status=IN_PROGRESS)`
     `[FIRESTORE_SYNC] quiz_attempts/50 (user=5 result=NÃO APROVADO score=0/30)`
   - Isso significa: conta de aluno criada, progresso de lição e resultado de simulado **caem no Firestore em <1s**, sem latência perceptível ao cliente (fila assíncrona).
   - Validação automatizada de ponta a ponta: `npm run verify:firebase` (20 checks: credenciais → SDK init → dual-write register/progress/quiz → bulk-sync → status → health).

### 24.6 Segurança das Credenciais
- `firebase-service-account.json` e `.env` BLOQUEADOS no `.gitignore` (nova entrada adicionada).
- Também bloqueados: `*.service-account.json`, `.firebaserc`, `firebase-debug*.log`, `backup-pre-migracao*`.
- **NUNCA commitar a chave privada.** Para deploy em produção, use GOOGLE_APPLICATION_CREDENTIALS via secret manager ou volume.
